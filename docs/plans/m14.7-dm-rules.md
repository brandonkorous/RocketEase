**Status:** built and verified live against the dev server + worker, 2026-09-06 (see the end of this

`images/conversations.png`) and in the Settings › Automations builder, so no mockup was needed.

## What it is

Before a direct message goes out — from the composer, from a drafted reply, from a rule — RocketEase says
whether it can be sent and, when it cannot, why. The rules come from the networks' own documents; the
one rule the networks did not publish is declared as RocketEase's own.

## Decisions

- **One decision, four readers.** `sendDecision` (`lib/engagement/messaging/window.ts`, pure) answers
  "can this direct message go out now?"; `replyDecision` (`decide.ts`) plugs in the two counts it may
  need. The composer shows it, `resolveReplyTarget` and `sendDraftReply` enforce it on the server, the
  `inbox.saved_reply` rule action goes through the same `resolveReplyTarget`, and the worker asks again
  right before `adapter.reply`, because a reply queued inside the window can reach the front of the queue
  outside it. Public replies (comments, mentions, reviews) have no window and are not judged.
- **The window counts from what RocketEase has seen.** `conversation.last_inbound_at` is the customer's
  last message as ingested. Meta also opens the window on a reaction or a button tap, which never reach the
  inbox, so this window can be shorter than the network's, never longer. The composer says when it closes.
- **A cap waits; a closed window does not.** X's per-15-minute and per-day caps clear with time, so a
  reply that hits one is queued with `runAt` and the row reads "Waiting — …"; the worker re-checks and
  re-queues. A closed window is reopened only by the customer, so the composer disables Send and the
  worker records the reply as failed with the reason and an `inbox.reply_failed` notice.
- **RocketEase's own rule: one automated direct message per contact per 24 h**, on every network, with or
  without an approver (a rule-written message is automated either way). A person may always write.
  `message.rule_id` (migration 0031) records the rule that wrote a message; the thread reads
  "Sent by rule “…”" instead of the creator's name.
- **Human Agent is left to Meta's grant.** The adapter sends `messaging_type: RESPONSE` only. When Meta
  grants the Human Agent feature, the adapter can tag a person's reply between 24 h and 7 days; until then
  the composer tells the person Meta offers that path and that RocketEase has not been granted it.

## Definitions the product shows

- **Reply window** — the time after the customer's last message during which the network accepts a reply
  (Meta: 24 h). "Open until" is that message's time plus the window.
- **Waiting** — a reply held by a network cap that clears with time; the row says when it goes out.
- **Automated direct message** — a DM written by a rule (`message.rule_id` set), whether or not a person
  approved the run.

## Left out on purpose

- Sending the Human Agent tag: needs Meta's Human Agent permission, which the app has not been granted;
  nothing here pretends otherwise.
- Meta's "200 × engaged users" call budget as an enforced cap: at one message per call it is 200 messages
  per person per day, which an inbox reply never reaches; recorded in the table's note, not enforced.
- A `reply_window` fact for rules: on the `inbox.message_received` trigger the window has just opened, so
  the fact would always read "open".

## Live check (2026-09-06)

`apps/platform/e2e/.state/dm-rules-live/` (git-ignored): fresh tenant, demo network, one saved reply, one
rule made in the builder — "Auto-answer DMs" (`kind is message` → send the saved reply without review; the
builder shows the window hint under the checkbox). Messages went through the real webhook → worker path.

- A new DM: the rule's run is `applied`, the reply is `sent` with `rule_id` set, the thread reads
  "Sent by rule “Auto-answer DMs” ✓✓", and the composer reads "⏱ Reply window open until Sep 7, 2026,
  1:12 AM · Demo network allows a reply within 24 h of the customer's last message."
- The customer writes again: the rule's run is `skipped` — "RocketEase sends at most 1 automated direct
  message per contact per 24 h, and this contact already got one. A person can still reply." No second DM.
- The customer's last message backdated 25 h: the composer reads "⊘ Reply window closed · Demo network
  allows a reply within 24 h of the customer's last message; theirs was 25 h ago. Wait for them to write
  again." and Send is disabled.
- A reply queued straight into the worker after that: recorded `failed` with the same sentence, one
  `inbox.reply_failed` notice, the thread shows "Failed — …" with Retry.
- The customer writes again: the window reopens, a person's reply goes out and reads "Sent by DM Tester ✓✓".
- Settings › Automations lists the rule; its runs for this thread are applied, then skipped with the reason.
